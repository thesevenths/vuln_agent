 **`attack_surface.json` 不会一次性全量发给 LLM**。架构上采用了"全量采集 → 按需切片"的模式。以下是具体消费方式：

---

## 消费架构总览

```
attack_surface.json (全量 ~4500 行)
        │
        ├──── coverage_summary ──→ 统计数字（~10行）注入 LLM
        │
        ├──── attack_paths ─────→ 按 candidate handler 过滤（≤5条）注入 LLM
        │
        ├──── entry_points ─────→ 仅在 logic_scan 交叉分析时作为集合使用
        │
        ├──── sensitive_ops ─────→ 仅在 logic_scan 交叉分析时作为集合使用
        │
        └──── recon_query_results ──→ 作为 checkpoint_merge 缓存复用，避免 Joern 重跑
```

## 1. 摘要统计 — 全局只注入数字

[`_build_logic_l2_block`](file:///e:/model-similarity/agent/joern_vuln_scanner.py#L896-L910) 只提取 `coverage_summary` 的统计数字：

```
### Recon 攻击面摘要
- 入口总数: 185
- 受保护入口: 120
- 无鉴权入口: 65
- 敏感操作总数: 42
- 攻击路径: 87
- 无鉴权路径: 33
- CWE 缺失分布: CWE-306=12, CWE-862=25
```

这部分大约 **10 行文本**，成本极低。

## 2. 攻击路径 — 逐候选过滤，最多 5 条

[`_build_logic_l2_block`](file:///e:/model-similarity/agent/joern_vuln_scanner.py#L912-L936) 中，对**每一个漏洞候选**，只找与该候选 `caller` 相关的攻击路径：

```python
relevant_paths = [
    p for p in attack_surface.get("attack_paths", [])
    if caller and (p.get("entry") == caller or p.get("sink") == caller)
]
for rp in relevant_paths[:5]:  # 最多 5 条
```

输出是紧凑的单行调用链：
```
### 当前候选攻击路径 (2 条)
- SqlInjectionLesson8.completed → jdbcTemplate.update [❌ 无鉴权] 缺失: ['CWE-862']
- SqlInjectionLesson8.completed → executeQuery [❌ 无鉴权] 缺失: ['CWE-862']
```

**每个候选只看到自己的 2-5 条路径**，不是全部 87 条。

## 3. 入口 + 敏感操作 — 用于交叉分析，不直接进 LLM

`entry_points` 和 `sensitive_operations` 主要在 [`_extract_logic_candidates`](file:///e:/model-similarity/agent/joern_vuln_scanner.py#L2696) 中做集合交叉：

- `endpoint_enumeration` 结果 ∩ `auth_guards` 结果 → 找出**无鉴权的端点**
- `sensitive_operations` ∩ 无鉴权端点 → 生成**漏洞候选**

这一步是纯程序逻辑（set 运算），**不消耗 LLM token**。

## 4. LLM 每次收到的完整上下文

在 [`_analyze_logic_candidate`](file:///e:/model-similarity/agent/joern_vuln_scanner.py#L4137) 中，每个候选的 LLM prompt 包含：

| 材料 | 来源 | 大小 |
|------|------|------|
| 方法源码 | `_fetch_method_source(caller)` | ~50行代码 |
| 调用链源码 | `_fetch_caller_chain_source(caller)` | ~100行代码 |
| 相关查询切片 | `_build_logic_related_context_block` | 只含 caller 相关行 |
| **攻击面摘要** | `coverage_summary` 数字 | ~10行 |
| **攻击路径** | 过滤后 ≤5 条 | ~5行 |
| CWE 分析指引 | Skill 模板 reasoning_workflow | ~30行 |
| 源码字面量 | `extract_source_literals` | ~12行 |

**总 LLM 输入约 200-400 行**，远不是 4500 行的全量文件。

## 5. Planner 层面的使用

Planner 不直接消费 `attack_surface.json` 内容，而是用 metadata 决策下一步动作：

```python
# planner.py:2038-2050
if not state.metadata.get("java_route_count", 0):
    state.metadata["logic_attack_surface_attempted"] = True
    # 触发 java_attack_surface skill
```

Planner 决定"是否需要做更深的审计"，而不是分析具体数据。

---

**总结**：`attack_surface.json` 是一个**全量知识库**，下游通过"摘要统计 + 按候选过滤 + 集合交叉"三种方式按需切片，LLM 每次只收到与当前候选相关的极小切片（约 15 行），上下文完全可控。
